# API и сетевой слой

Как Android-клиент общается с бэкендом. Контракт описан в `../swagger.yml`,
но расходится с реальностью — что из него действительно поднято, видно в
`../backend/configs/static_config.yaml` и в разделе «Состояние стенда».
Здесь — что уже реализовано, что только описано типами, и где какие грабли.

## Подключение

| Параметр | Значение |
| --- | --- |
| Base URL | `http://158.160.155.144:8080/api/v1/` |
| Авторизация | `Authorization: Bearer <access_token>` |
| Формат | JSON, поля в `snake_case` |

Base URL задаётся через `buildConfigField("String", "API_BASE_URL", ...)` в
`app/build.gradle.kts` и читается из `ApiConfig.BaseUrl`. В коде фич
`BuildConfig` не трогаем. Локальный бэкенд подставляется без правки файла:

```
./gradlew :app:installDebug -PapiBaseUrl=http://10.0.2.2:8080/api/v1/
```

Три момента, на которых легко потерять время:

- **Завершающий слэш в base URL обязателен.** Без него Ktor заменит последний
  сегмент пути: `.../api/v1` + `auth/login` → `.../api/auth/login`.
- **`localhost` на эмуляторе — это сам девайс.** Бэкенд на машине разработчика
  доступен по `http://10.0.2.2:8080`, на физическом устройстве — по адресу
  машины в локальной сети.
- **HTTP без TLS разрешён только в debug.** Android с API 28 режет cleartext,
  поэтому в `app/src/debug/AndroidManifest.xml` стоит `usesCleartextTraffic`.
  В release-сборке этого разрешения нет, а стенд работает по HTTP — значит
  release с сетью сейчас не соберётся рабочим. Пока у бэкенда нет HTTPS,
  проверяем только debug.

## Устройство сетевого слоя

```
core/network/
  ApiConfig.kt            base URL и таймауты
  ApiJson.kt              общая настройка Json
  HttpClientFactory.kt    сборка единственного HttpClient
  AuthTokenProvider.kt    чтение токена (нужно клиенту)
  AuthTokenStore.kt       чтение + запись + Flow токена (репозиторий авторизации)
  EncryptedAuthTokenStore.kt  боевое хранилище: EncryptedSharedPreferences
  InMemoryAuthTokenStore.kt   только для тестов
  ApiCall.kt              apiCall { } — маппинг ошибок Ktor в доменные
  NetworkException.kt     разбор тела ошибки в ValidationErrorDto
  HttpMethod.kt           какие методы можно повторять
  Throwable.kt            классификация исключений
  dto/                    ApiErrorDto, ValidationErrorDto
core/domain/
  NetworkException.kt     доменная ошибка сети
core/di/NetworkModule.kt  HttpClient, Json и токен-хранилище в Koin
```

Правила: репозиторий фичи инъектит готовый `HttpClient`, свой не собирает;
каждый вызов заворачивается в `apiCall { }`; DTO не поднимаются выше `data/`.

### Ошибки

`apiCall { }` сводит всё к `NetworkException`:

| Ситуация | Тип |
| --- | --- |
| нет сети, DNS, хост недоступен | `NoConnection` |
| истёк таймаут | `Timeout` |
| 401 | `Unauthorized` |
| 403 | `Forbidden` |
| 404 | `NotFound` |
| прочие 4xx | `ClientError(code)` |
| 5xx | `ServerError(code)` |
| тело не разобралось | `Serialization` |
| остальное | `Unknown` |

Исходный `ResponseException` сохраняется в `cause` — оттуда достаётся тело
ошибки (`ApiErrorDto`, `ValidationErrorDto`) там, где фиче важен не только
статус.

### Повторы

Повторяются **только `GET` и `HEAD`** — на 5xx и на обрыв соединения, до двух
раз с экспоненциальной паузой. `POST` не повторяется сознательно: шлюз может
ответить 5xx уже после того, как бэкенд принял запрос, и ретрай `POST
/projects/{id}/generate` создал бы вторую фоновую задачу. `GET` статус-ручки
под ретрай 5xx попадает — и это правильно.

## Реализовано

Проверено на живом стенде: `AuthApiIntegrationTest` гоняет настоящий
`AuthRepositoryImpl` по сети. По умолчанию тест пропускается — в CI ему в сеть
не место:

```
API_INTEGRATION=1 ./gradlew :app:testDebugUnitTest --tests '*AuthApiIntegrationTest'
```

### `POST /auth/register`

`AuthRepository.register(email, password, nickname)` → `AuthSession`.

| Ответ | Поведение |
| --- | --- |
| 201 | `AuthSession`, токен сохраняется в `AuthTokenStore` |
| 400, 422 | `AuthException.FieldRejected(field)` — значение отверг сервер |
| 409 | `AuthException.RegistrationConflict(field)` — email или никнейм заняты |

`422 Unprocessable Entity` разбирается так же, как `400`: это типовой ответ
валидации, и тело у него то же самое.

Поле формы берётся из `ValidationError.code`, у всех этих статусов тело одинаковое:

| Код | Поле |
| --- | --- |
| `INVALID_EMAIL`, `EMAIL_EXISTS` | `Field.Email` |
| `INVALID_PASSWORD` | `Field.Password` |
| `INVALID_NICKNAME`, `NICKNAME_EXISTS` | `Field.Nickname` |
| незнакомый код | `Field.Unknown` |

Правила валидации живут на бэкенде и на клиенте **не продублированы** — иначе
разъедутся при первом же его изменении. Сейчас там: пароль 8–128 символов
обязательно с буквой и цифрой, никнейм 3–64 символа, email по regex и до 128
символов. Сообщения сервера английские (`"Password must be 8-128 chars…"`),
показывать их пользователю нельзя — экран сам подбирает текст по `field`.

### `POST /auth/login`

`AuthRepository.login(email, password)` → `AuthSession`.

| Ответ | Поведение |
| --- | --- |
| 200 | `AuthSession`, токен сохраняется в `AuthTokenStore` |
| 400, 422 | `AuthException.FieldRejected(field)` — тем же разбором `ValidationError`, что и регистрация |
| 401 | `AuthException.InvalidCredentials` — неверная пара логин/пароль, а не «сессия протухла»; токен не трогаем |

`AuthRepository.logout()` — локальный сброс токена, ручки на бэкенде нет.

Токен кладёт в хранилище сам репозиторий: дальше `HttpClient` подставляет
заголовок на каждом запросе, и вызывающему коду не нужно об этом помнить.
Хранится он в `EncryptedSharedPreferences` (ключ — в Android Keystore,
`EncryptedAuthTokenStore`) и переживает перезапуск приложения. Файл читается
один раз лениво, дальше значение отдаётся из кэша: клиент спрашивает токен на
каждом запросе, а каждое чтение — расшифровка через Keystore.
`InMemoryAuthTokenStore` остался для тестов, где Android-контекста нет.

Пользователя из того же ответа (`id`, `email`, `nickname`) репозиторий кладёт в
`AuthUserStore` — общий `DataStore<Preferences>` из `coreModule`, без шифрования:
это не секрет доступа, а идентификаторы, которые и так видны в любом ответе API.
Наружу он виден как `AuthRepository.currentUser: Flow<AuthUser?>`; вкладка
профиля берёт из него свой `userId`, потому что ручки `/auth/me` в API нет.

**Рассинхрон «токен есть, пользователя нет».** Токен и профиль лежат в разных
хранилищах, поэтому состояние `isAuthorized == true` при `currentUser == null`
возможно — и оно ровно у всех, кто вошёл до появления `AuthUserStore`.
Дозаполнить нечем (`/auth/me` нет, а `GET /users/{id}` требует того самого id),
поэтому вкладка профиля в этом случае показывает пустое состояние «войдите
заново», а список чатов — пустой список.
Принудительного разлогина нет — он относится к обработке протухшего токена,
которой пока нет вовсе.

Наличие сессии наружу отдаёт `AuthRepository.isAuthorized: Flow<Boolean>` —
по нему навигация выбирает стартовый экран. Проверки валидности сохранённого
токена при старте нет (ручки `/auth/me` в API нет), авто-разлогина по 401/403
и logout в UI тоже пока нет: сменить аккаунт можно только через «Очистить
данные» в настройках Android.

### Нормализация email

Репозиторий приводит email к нижнему регистру и обрезает пробелы, никнейм —
только обрезает. Пароль не трогаем: пробелы в нём значимы.

Это не косметика. Бэкенд ищет пользователя точным сравнением
(`WHERE email = $1`) и при регистрации адрес не нормализует. Без приведения
`Ivan@mail.ru` и `ivan@mail.ru` — два разных аккаунта, а вход «тем же» адресом
даёт 401. Автокапитализация на клавиатуре телефона делает это регулярно.

### `POST /projects` и `GET` / `PATCH` / `DELETE /projects/{id}`

`ProjectRepository` (`feature/project`): `createProject`, `getProject`,
`updateProject`, `deleteProject`. Клиент инъектит готовый `HttpClient`, каждый
вызов — в `apiCall { }`. Методы возвращают `Result` и не бросают (кроме отмены
корутины): при ошибке в `failure` лежит `NetworkException`, разбор — во ViewModel.

| Метод | Поведение |
| --- | --- |
| `createProject(name, description, prompt)` | `POST /projects`, тело `{name, description, prompt}`, ответ **`202`** + `Project` с полем `job_id` → доменный `ProjectCreation`. Требует `Bearer`. Пустой промпт или длиннее 5000 символов → `400 ClientError` (клиент до этого не доводит: кнопка неактивна, поле обрезается) |
| `getProject(id)` | `GET`, отдаёт доменный `Project`. `Bearer` опционален (публичный проект доступен без токена). `404 → NotFound`, `403 → Forbidden` |
| `updateProject(id, isPublic?, canvas?)` | `PATCH`, тела в ответе нет. `null`-аргумент = «не трогать поле» (`explicitNulls = false`). Требует `Bearer`, `403` не автор |
| `deleteProject(id)` | `DELETE`, тела в ответе нет. Требует `Bearer` |

`name` и `description` в теле создания — не опциональные поля: бэкенд читает их
с дефолтом `""`, поэтому пустое описание уходит пустой строкой, а не пропадает.
Имя бэкенд больше не требует, но пустым его не отправляем: проект без заголовка
встал бы безымянным и в список чатов, и в шапку своего экрана, поэтому форма
подставляет `"Untitled project"`.

**Создание запускает первичную генерацию** (бэкендовый PR 290, `main` от
24.08.2026). Ручка перестала быть «создать пустой проект»: `prompt` обязателен,
бэкенд синхронно пишет его в историю чата, ставит фоновую задачу и отвечает
`202` с `job_id`. Разбирать `202` отдельно не нужно: ошибкой Ktor считает только
4xx/5xx, `apiCall { }` его не трогает.

**Лимит промпта здесь — 5000 UTF-8 символов, а не 1500 байт.** Это разные
хендлеры: 1500 **байт** меряет `POST /projects/{id}/generate` (правки в чате,
см. ниже), 5000 **символов** (`Utf8Length`) — создание. Константы на клиенте
тоже разные и переиспользованию не подлежат:
`feature/createproject/ui/CreatePromptLimit.kt` против
`feature/project/ui/PromptInputLimit.kt`. Спутать их легко, цена — `400` на
отправке.

Ошибки создания: `400` с телом `{message}` — `"Prompt cannot be empty"`,
`"Prompt is too long (max 5000 characters)"`,
`"references supports at most 2 project ids"`; плюс `401` и `500`.

Поля `model` и `references` (до двух id проектов-референсов) в теле есть, но
клиент их не шлёт и в DTO не заводит: UI под них нет, дефолт модели
(`deepseek-v4-flash/latest`) бэкенд ставит сам. То же с полем `data`
(копирование чужого публичного SVG вместо генерации) — это сценарий витрины, а
не формы создания; ответ на него `201` **без** `job_id`, поэтому `job_id`
в `ProjectDto` nullable.

**Форма генерацию не ждёт.** Пришёл `202` — уходим на экран проекта; промпт там
уже виден, потому что бэкенд записал его в историю синхронно. Само ожидание —
`GET /projects/{id}/generate/{job_id}`, тот же эндпоинт и та же обвязка
(`ChatRepository.awaitGeneration`), что у правок в чате — живёт на экране
проекта, в его `viewModelScope`. Сам `job_id` доезжает туда навигацией:
у маршрута `Destination.Project` он необязательный **query**-аргумент
(`project/{projectId}?jobId={jobId}`) — из списка чатов и из профиля на тот же
экран приходят без него. `ProjectViewModel` получает его параметром
(`initialJobId`) и ждёт ровно один раз, в конце первой загрузки ленты.

**Создание живёт здесь, а не в `feature/createproject`.** У формы создания
своего репозитория нет: ответ `POST /projects` — это тот же `ProjectDto` и та
же доменная модель `Project`, а DTO выше `data/` своей фичи не поднимаются.
`CreateProjectViewModel` инъектит `ProjectRepository` из `projectModule`
(прецедент такой кросс-фичевой зависимости по `domain/` уже есть:
`ProfileRepository` отдаёт `FeedProject` из `feature/feed`).

`createProject` и `getProject` маппят `ProjectDto → Project` в
`data/ProjectMappers.kt`. `id` и `name` в доменной модели не-nullable: их
отсутствие в ответе — сломанный контракт, маппер бросает
`NetworkException.Serialization`. Отсутствие `is_public` трактуется как
приватный (задокументированный дефолт).

`data` — это **SVG-строка** (не объект), плюс есть `url` (S3-ссылка на объект,
пусто у пустого проекта). Прежние `ProjectDataDto`/`ProjectCanvas` моделировали
`data` объектом — это расходилось с контрактом, поэтому убраны. У профиля
`ProjectDescriptionDto` поле `url` пока не заведено — отдельная правка.

Вживую **не проверено**: на 13.08 `POST /projects` падал 500 (заглушка
сохранения в S3), поэтому id живого проекта было не получить и интеграционного
теста нет. Контракт покрыт `ProjectRepositoryImplTest` на `MockEngine`. На UI
заведено только создание: форма `feature/createproject` уходит на экран проекта
с настоящим id из ответа. Перед приёмкой стенд перепроверить.

### Версии проекта: `GET /versions`, `GET /versions/{id}`, `POST /restore`

`VersionsRepository` (`feature/project`): `getVersions`, `getVersionUrl`,
`restoreVersion`. Отдельный репозиторий, а не методы в `ProjectRepository`:
у версий свой ресурс, свои DTO и своя политика доступа. Как и везде — `apiCall`
внутри, `Result` наружу.

| Метод | Поведение |
| --- | --- |
| `getVersions(projectId)` | `GET /projects/{id}/versions`, ответ `{versions: [{id, version_num, created_at}]}`. Порядок серверный (`ORDER BY version_num DESC`, новые сверху), на клиенте не пересортировываем. Пагинации нет — приходят все версии |
| `getVersionUrl(projectId, versionId)` | `GET /projects/{id}/versions/{versionId}`, ответ `{version_id, url}`. Отдаём наружу только `url`: `version_id` — эхо пути, нового знания в нём нет |
| `restoreVersion(projectId, versionId)` | `POST /projects/{id}/versions/{versionId}/restore`, ответ `{version_id, url}` → доменный `VersionRestore` |

**История приватна даже у публичного проекта.** Все три ручки требуют `Bearer`
и сверяют `author_id` с пользователем из токена: не автор → `403 Forbidden`
без исключений по `is_public`. Нет проекта или версии → `404 NotFound`,
нет заголовка `Authorization` → `401`.

**Тела ошибки у этих ручек нет.** В отличие от `create`/`delete`, хендлеры
версий отвечают голым статусом (`SetResponseStatus(...); return {};`) — ключа
`message` в ответе не будет, и `NetworkException.serverMessage` останется
`null`. Разбор ошибки в UI должен опираться на тип, а не на текст.

**Откат не перематывает историю, а удлиняет её.** `restore` читает старую
версию и сохраняет её содержимое как новую (`version_num = MAX + 1`), поэтому
`version_id` в ответе — это id **новой** версии, а не той, к которой
откатывались. После отката список версий надо перезапросить: номера новой
версии в ответе нет.

**Тело у `POST /restore` — `{}`, а не пустое.** Полей запрос не имеет, но
хендлер наследует `HttpHandlerJsonBase` и парсит тело как JSON до собственной
логики. Отдельный DTO ради этого не заводим — шлём константный `TextContent`.

**Ретраев на `restore` нет** и быть не должно: политика `installApiRetry`
повторяет только `GET`/`HEAD` (`core/network/HttpMethod.isRetryable`). Повтор
после 5xx от шлюза создал бы второй откат, то есть лишнюю версию. Закреплено
тестом `restoreVersion не повторяется при 5xx`.

`url` в ответах версий — **presigned S3-ссылка с TTL в час**
(`presigned-url-ttl-seconds: 3600`), кроме `restore` у публичного проекта: там
отдаётся публичная ссылка. Хранить её дольше часа бессмысленно — протухнет в
403 от S3.

Ссылки в списке версий нет вообще: чтобы показать превью каждой версии, нужен
отдельный запрос на каждую. Отсюда решение в чате — показывать превью только у
последней версии (её `url` уже есть в `GET /projects/{id}`). Бэкенду заведён
тикет: отдавать `url` прямо в элементах списка.

`created_at` версии сериализуется явно, `%Y-%m-%dT%H:%M:%S%Ez` в UTC — то есть
`2026-08-16T12:34:56+00:00`, с офсетом, а не с `Z`, и без миллисекунд. Разбирает
его общий `data/InstantParsing.kt` (вынесен из `ProjectMappers`, чтобы обе
фичевые мапперы не расходились в трактовке). Кривой формат даёт `null`, а не
ошибку; отсутствие `id` или `version_num` — наоборот, `Serialization`.

Разбирать этот формат обязан `OffsetDateTime.parse`, а не `Instant.parse`:
офсет вместо `Z` последний принимает только с JDK 12, а на устройстве
`java.time` берётся из libcore (десугаринг не подключён, minSdk = 26) — на
Android 8–13 это OpenJDK 8/11, где строка с `+00:00` падает. Проверено на
1.8.0_501. Unit-тесты идут на JDK 17 и такую ошибку не показывают, поэтому
порядок веток в парсере менять нельзя.

Ещё одно расхождение: невалидный UUID в пути бэкенд не валидирует, каст
`$1::uuid` падает в необработанное исключение → `500`. Клиент id из своих
ответов и берёт, но заводить их руками нельзя.

UI версий в этом PR нет — только сетевой слой; экран истории и откат
отдельной задачей. Вживую не проверено (см. состояние стенда), контракт покрыт
`VersionsRepositoryImplTest` на `MockEngine`.

### История диалога: `GET /projects/{id}/chat`

`ChatRepositoryImpl` (`feature/project`) собирает экран проекта из **трёх
параллельных** запросов: `GET /projects/{id}` (название, видимость и `url`
последней версии), `GET /projects/{id}/chat` (сообщения) и
`GET /projects/{id}/versions` (нужен ровно для одного — узнать `id` последней
версии, чтобы понять, к какому пузырю относится `url` из проекта). Проект и
версии идут через готовые `ProjectRepository` и `VersionsRepository`, свой
запрос здесь один — за историей.

Ответ — `{chat_history: [{role, text?, version_id?, error?, job_id?, created_at}]}`,
порядок добавления (старые сверху). Записи пишутся **парами**, обе — из
асинхронной генерации, и у пары общий `job_id`:

```json
{"role": "user",      "text": "<промпт как есть>", "job_id": "...", "created_at": "..."}
{"role": "assistant", "version_id": "<id версии>", "job_id": "...", "created_at": "..."}
{"role": "assistant", "error": "<текст ошибки>",   "job_id": "...", "created_at": "..."}
```

Отсюда всё поведение клиента:

- **У ответа ассистента нет ни своего текста, ни ссылки** — либо `version_id`
  (тот же, что в `GET /versions`), либо `error` с текстом провала. Текст пузыря
  успешного ответа берётся из `strings.xml`, ссылка на превью — из
  `GET /projects/{id}`, но только для последней версии; остальные ссылки клиент
  добывает по требованию (`getVersionUrl`): сверился по `version_id` с кэшем,
  промахнулся — сходил за свежей.
- **История ≠ список версий.** Версию создают ещё два места, и ни одно в чат не
  пишет: `PATCH` с `data` и `POST /restore`. `POST /projects` — исключение:
  с 24.08.2026 он кладёт промпт в историю сам и его первичная генерация приходит
  в ленту обычным ответом ассистента. Поэтому разделители в ленте нумеруются **по порядку удачных
  ответов ИИ** (1, 2, 3…), а не по `version_num`: иначе первый же ответ получил
  бы «Version 2 saved». Провалившийся ответ версии не создаёт и номер не
  двигает — разделителя под ним нет. Откаты в ленте не видны совсем — тикет
  заведён.
- **Промпт попадает в историю сразу при старте задачи**, до обращения к модели
  (`AppendUserMessage` перед запуском фоновой корутины). Поэтому «осиротевший»
  промпт без ответа под ним — это **норма**: генерация ещё идёт. Провал теперь
  тоже попадает в историю — записью с `error`.
- **`job_id` связывает промпт с ответом на него.** По нему клиент узнаёт свой
  ответ в перечитанной ленте и находит результат генерации, если статус-ручка
  потеряла задачу (см. ниже). Маппер кладёт его в `ChatMessage.Incoming` и
  `ChatMessage.Failed`.
- **У записей нет `id`** — ключ для `LazyColumn` собираем сами:
  `chat-<индекс>-<роль>`. История append-only, индекс стабилен между запросами.
- **Ни пагинации, ни лимита** — весь массив целиком при каждом открытии экрана.

**История приватна**: только автору, 403 даже у публичного проекта — как и у
версий. Нет проекта → 404.

**Деградация вместо ошибки.** `getChat` возвращает `failure` только если упал
`GET /projects/{id}` — без него у экрана нет даже заголовка. Ошибки `/chat` и
`/versions` (403 у не-автора, 404, 5xx) съедаются: лента остаётся с одной
системной пилюлей, проект открывается на чтение. Кривая запись (неизвестная
роль, промпт без текста, ответ без `version_id` **и** без `error`) пропускается,
а не роняет разбор.

`created_at` здесь приходит **не из хендлера, а прямо из Postgres**
(`jsonb_build_object('created_at', NOW())`) — то есть с микросекундами:
`2026-08-16T09:12:33.123456+00:00`. Это третий формат времени в API (после
`time_point` у `/users/{id}` и явного RFC3339 у остальных ручек); все три
разбирает общий `data/InstantParsing.kt`. Неразобранное время даёт `null` —
пузырь просто рисуется без подписи.

### Генерация: `POST /projects/{id}/generate` + опрос статуса

Генерация **асинхронная**: `POST` только ставит задачу, результат забирают
опросом. Один вызов на два метода репозитория — `startGeneration` и
`awaitGeneration`: экран должен показать скелетон ответа сразу по `job_id`, не
дожидаясь картинки.

**Шаг 1 — старт.** `POST /projects/{id}/generate`, тело `{prompt, model}`, ответ
**202** `{job_id}`. Отвечает за миллисекунды — своего таймаута у запроса нет,
общих 30 с хватает. Поле `model` заполняется выбранной в чате моделью —
**коротким** именем без префикса `gpt://` (см. `GET /models`). При `null`
`explicitNulls = false` выкидывает поле из JSON, и бэкенд подставляет свой
дефолт `deepseek-v4-flash/latest` (`generate_project.cpp:31`).

| Код | Что значит |
| --- | --- |
| 202 | задача поставлена, в теле `job_id` |
| 400 | промпт пуст либо длиннее 1500 байт |
| 401 | нет токена или он битый |
| 403 | чужой проект |
| 404 | проекта нет |

**422 и 503 из этой ручки исчезли** — провал генерации приходит через
статус-ручку, а не кодом ответа на старт.

Две особенности, которых нет у остальных ручек:

- **лимит промпта — 1500 байт UTF-8, не символов** (`prompt.size()` в C++
  считает байты, кириллица — по два). Дублируем его на клиенте
  (`feature/project/ui/PromptInputLimit.kt`), чтобы не ловить 400. У промпта
  при создании проекта лимит **другой** — 5000 символов, см. выше;
- **ретраев нет и быть не должно**: `POST` не подпадает под `isRetryable`,
  повтор после 5xx шлюза создал бы вторую задачу и вторую пару сообщений в
  истории.

К моменту успешного ответа промпт **уже лежит в истории чата**. Поэтому убрать
его с экрана и вернуть текст в поле ввода можно ровно в одном случае — если
упал сам `POST`.

**Шаг 2 — опрос.** `GET /projects/{id}/generate/{job_id}`, long polling: запрос
«подвисает» на сервере до 25 секунд и отвечает одним из трёх:

```json
{ "status": "pending" }                        // повторить запрос
{ "status": "done",  "url": "https://s3/..." } // presigned на SVG новой версии
{ "status": "error", "message": "..." }        // генерация упала
```

Незнакомый статус клиент трактует как `pending` — спрашивает ещё раз, а не гадает.

Клиентские тайминги — `ApiConfig`: `StatusPollTimeoutMillis` (40 с на запрос;
25 с сервер держит сам, остальное — запас на сеть), `StatusPollGuardMillis`
(1 с, предохранитель от горячего цикла) и `GenerationDeadlineMillis` (5 минут —
общий дедлайн ожидания). В `ChatRepositoryImpl` они приходят параметром
`GenerationPolling`, чтобы тест не ждал пять минут по-настоящему.

`GET` под общий ретрай 5xx попадает автоматически — так и надо. Таймаут и обрыв
связи ожидание не прерывают: задача на сервере от моргнувшей сети никуда не
девается.

| Код | Что делает клиент |
| --- | --- |
| 200 `done` | версия готова — перечитывает ленту (см. ниже) |
| 200 `error` | пузырь ошибки в ленте + «Повторить» |
| 401, 403 | локальный пузырь ошибки; ленту **не** перечитывает |
| 404 | fallback на историю (см. ниже) |

**Ответ приходит раньше, чем появляется в истории.** Бэкенд будит опрос статуса
(`entry->cv.NotifyAll()`) **до** того, как допишет результат в `chat_history`, а
сама запись у него best-effort — при падении она только логируется. Поэтому по
`done` и `error` экран перечитывает ленту не один раз, а до трёх с паузой в
полсекунды, пока в ней не появится ответ **со своим `job_id`**. Не дождался —
ленту не подменяет: на `done` просто снимает скелетон, на `error` рисует пузырь
с текстом из ответа опроса. Иначе перечитанная лента заменила бы собой и промпт,
и скелетон, не дав взамен ничего, — результат генерации пропал бы с экрана до
следующего открытия.

**Записи об исходе на сервере может не быть вообще** — тогда перечитывать нечего.
Так бывает, когда опрос сорвался сам (401, 403, 5xx после ретраев, неразобранный
ответ) или когда 404-фолбэк ничего не нашёл: генерация, возможно, ещё идёт, и
никакой ошибки сервер не записывал. В этих случаях репозиторий отдаёт
`Result.failure`, а экран рисует **локальный** пузырь ошибки, не трогая ленту.

**404 — не сразу ошибка.** Задача живёт **в памяти процесса бэкенда** (30 минут
после завершения, 60 — если зависла в `pending`), и его рестарт её теряет — в
том числе уже после успешной генерации. Поэтому на 404 клиент перечитывает
историю и ищет в ней ответ ассистента со своим `job_id`: нашёл `version_id` →
успех, нашёл `error` → провал, не нашёл → **ошибка** (исход неизвестен: задача
могла оборваться вместе с процессом, а могла и досчитаться). Пара попыток с
паузой: запись в историю могла отстать от рестарта.

**Дедлайн 5 минут — не провал.** Задача могла остаться считаться; экран говорит
«генерация ещё идёт, загляните позже» и оставляет промпт в ленте. Результат
будет виден при следующем открытии чата.

**Ожидание живёт в `viewModelScope`.** Ушёл с экрана — опрос умер, бэкенд
доводит генерацию до конца сам. Ни `WorkManager`, ни хранения `job_id` на диске
не заводим.

**«Повторить»** заводит **новую задачу и новую пару сообщений** — бэкенд ничего
не перезаписывает, дубль промпта в истории неизбежен.

Контракт покрыт `ChatRepositoryImplTest` на `MockEngine` (202, `pending`→`done`,
`error`, все три ветки 404-фолбэка, обрыв сети между опросами, дедлайн).

### Список моделей: `GET /models`

`GenerationModelRepository` (`feature/project`): `getAvailableModels`,
`getSelectedModelId`, `selectModel` — справочник и настройка в одном
репозитории, это одно понятие «модель генерации». Авторизация **не требуется**:
блока `auth:` у ручки в `static_config.yaml` нет.

Ответ — `{object, data: [{id, object, owned_by, created}]}`:

```json
{
  "object": "list",
  "data": [
    { "id": "gpt://b1gttnvmtpd0tagdlb7o/deepseek-v4-flash/latest",
      "object": "model", "owned_by": "DeepSeek", "created": 0 },
    { "id": "gpt://openai/gpt-5.6-luna", "owned_by": "OpenAI" }
  ]
}
```

**Гарантирован только `id`.** `required` в swagger не проставлен (общее правило,
см. «Известные расхождения»), а сам ответ — отфильтрованный проброс Yandex AI
Studio плюс опциональная запись OpenAI, у которой есть лишь `id` и `owned_by`,
без `object`/`created`. Поэтому в DTO nullable всё, а записи без `id` маппер
отсеивает.

**Список короткий, и пустой — валидный ответ.** Бэкенд фильтрует ответ Studio
allow-list'ом из трёх яндексовых моделей (`get_models.cpp:57-78`):
`deepseek-v4-flash/latest`, `gpt-oss-120b/latest`, `qwen3-235b-a22b-fp8/latest`.
Запись OpenAI (`gpt://openai/gpt-5.6-luna`) дописывается сверху, только если у
процесса выставлен `OPENAI_API_KEY` (`get_models.cpp:80-91`). Итого длина
списка — от 0 до 4: разойдётся allow-list с тем, что отдаёт Studio, — `data`
придёт пустым.

**`id` отсюда нельзя слать в `generate` как есть — префикс нужно срезать.**
`/models` отдаёт полные URI, а генерация ждёт **короткое** имя и клеит префикс
сама (`LLMClientComponent.cpp:456-457`):

```cpp
const bool is_openai = IsOpenAIModel(model);
request_body["model"] = is_openai ? model : "gpt://b1gttnvmtpd0tagdlb7o/" + model;
```

а `IsOpenAIModel()` (`llm_models.hpp:11`) сравнивает с голым `gpt-5.6-luna`.
Проброс `id` как есть ломает обе ветки:

| `id` из `/models` | если прислать как есть | что нужно прислать |
| --- | --- | --- |
| `gpt://b1gttnvmtpd0tagdlb7o/deepseek-v4-flash/latest` | двойной префикс `gpt://…/gpt://…` | `deepseek-v4-flash/latest` |
| `gpt://openai/gpt-5.6-luna` | `IsOpenAIModel` = false → уедет в Yandex API | `gpt-5.6-luna` |

Правило одно на обе ветки: **срезать `gpt://` и первый сегмент после него**.
Срезка живёт в маппере `data/`, наружу репозиторий отдаёт уже готовый к
отправке короткий `id` — полный URI выше `data/` не поднимается. Завязка на
формат `gpt://<folder>/<model>` при этом остаётся: сменит бэкенд схему URI —
сломается молча, и промпт уедет с мусорным именем модели.

**Ответ приезжает под `application/octet-stream`, а не `application/json`.**
`GetModels` — единственная используемая приложением ручка на `HttpHandlerBase`
вместо `HttpHandlerJsonBase` (`get_models.hpp`), и `SetResponseContentType` в ней
не вызывается, поэтому userver ставит свой дефолт. Ktor'овский
`ContentNegotiation` такой ответ конвертеру не отдаёт вовсе, так что
`GenerationModelRepositoryImpl` читает тело `bodyAsText()` и разбирает его
`ApiJson` сам. Проверено на стенде 2026-08-24; починят заголовок на бэкенде —
разбор не сломается. Регрессия закрыта тестом
`octet-stream от бэкенда разбирается наравне с json`.

**Человекочитаемого имени модели в ответе нет** — ни `name`, ни `title`, только
`id` и необязательный `owned_by`. Тайтлы выводит клиент, поэтому новая модель на
бэкенде даст разные подписи на Android и iOS, пока обе платформы не дописать.

**`POST /projects` тоже принимает `model`** (`create_project.cpp:20`), но в
`CreateProjectRequestDto` его нет — первая генерация нового проекта остаётся на
серверном дефолте, и выбранная в чате модель на неё не влияет. Осознанно: поле
в DTO и пикер в форме создания — отдельным тикетом.

### `GET /users/{id}` — профиль и список проектов

Одна ручка на два экрана: профиль (`NetworkProfileRepository`) и список чатов
(`ChatsRepositoryImpl`). Ответ — поля пользователя плюс `projects[]`
(`ProjectDescriptionDto`: `id`, `name`, `description`, `is_public`,
`created_at`, `url`). Экраны независимы и ходят за ним по отдельности — дубль
запроса при переходе «список чатов → профиль» осознанный.

`Bearer` формально опционален, но **своему** профилю бэкенд отдаёт и приватные
проекты, а чужому проставляет `is_subscribed`, — поэтому запрос идёт с токеном.
Порядок — `ORDER BY created_at DESC`, свежие сверху; клиент не пересортировывает.
`url` есть только у проектов с сохранённой версией (`last_version_key`), у
остальных превью рисуется градиентом по id.

**`updated_at` в JSON нет** (в БД колонка есть, в ответе — нет). Подпись
«15 min ago» в списке чатов считается от `created_at`, то есть показывает время
создания проекта, а не последнего изменения — см. задачу бэкенду.

Свой id клиент берёт из `AuthRepository.currentUser` (ручки `/auth/me` нет).
Пользователь неизвестен — список пустой, в сеть не идём; отдельного состояния
«войдите» у вкладки пока нет.

Битый элемент `projects[]` (без `id` или `name`) **пропускается**, а не роняет
весь список; нечитаемое `created_at` даёт `null` и просто убирает подпись.
Покрыто `ChatsRepositoryImplTest` на `MockEngine`.

## Описано типами, не реализовано

DTO готовы, репозиториев и вызовов пока нет. Писать их вслепую по swagger
смысла мало — контракт ответов не подтверждён, см. состояние стенда выше.

Незакрытых строк здесь не осталось: `GET /users/{id}` переехал в
«Реализовано» (профиль и список чатов).

Авторизация: `Bearer` обязателен для `POST /projects`, `PATCH`, `DELETE` и
`generate`; для `GET /users/{id}` и `GET /projects/{id}` — опционален.

`ApiJson`: поля со значением `null` не попадают в JSON, а не уезжают как
`"is_public": null`, который бэкенд мог бы принять за сброс значения.

## Известные расхождения в контракте

- **Swagger описывает больше, чем есть.** Источник истины по факту — не swagger,
  а `backend/configs/static_config.yaml` и `backend/src/handlers/**`: там
  перечислены реально зарегистрированные пути. Списочных ручек (лента, «мои
  проекты») в них по-прежнему нет.
- **`name` против `nickname`.** `AuthResponse.user` отдаёт `nickname`,
  а `GET /users/{id}` — `name`. Одно и то же имя под двумя ключами; держим поля
  раздельно (`AuthUser.nickname` и `UserProfile.displayName`), чтобы не путать
  источники.
- **Битый токен даёт 403, а не 401.** То есть `NetworkException.Forbidden`.
  Авто-разлогин по 401 на него не сработает — учесть, когда будет обработка
  протухшей сессии.
- **Email регистрозависим на бэкенде.** Клиент это компенсирует (см. выше), но
  через веб и iOS дубли по регистру всё ещё создаются. Бэкенду нужен
  `lower(email)` в схеме.
- **`code` двух разных типов.** В схеме `Error` это число, в `ValidationError` —
  строка (`EMAIL_EXISTS`). Одним классом не разобрать, поэтому `ApiErrorDto` и
  `ValidationErrorDto` — разные типы.
- **`required` почти нигде не проставлен.** Обязательные поля есть только в
  `RegisterRequest`, `LoginRequest` и `AuthResponse` — только их DTO
  не-nullable. В остальных схемах поля формально опциональны, поэтому в Kotlin
  они nullable: приукрашивать контракт значениями по умолчанию не стоит, иначе
  отсутствие поля замаскируется нулём.
- **`/models` отдаёт JSON под `application/octet-stream`.** Ручка на
  `HttpHandlerBase` не выставляет content type, а `ContentNegotiation` разбирает
  только объявленный `application/json` — `body<T>()` падал бы ошибкой разбора
  на исправном ответе. Тело читаем строкой и парсим `ApiJson` вручную, см.
  `GET /models`.
- **`id` из `/models` непригоден для `generate` как есть.** Справочник отдаёт
  полные URI (`gpt://<folder>/<model>`), а генерация ждёт короткое имя и клеит
  префикс сама: яндексовая модель уехала бы с двойным `gpt://…/gpt://…`, а
  запись OpenAI не прошла бы `IsOpenAIModel` и ушла бы в Yandex API. Клиент
  срезает `gpt://` и первый сегмент после него — см. `GET /models`.
- **Нет обновления токена.** `refresh_token` в контракте отсутствует, токен
  назван долгоживущим. Когда он всё-таки протухнет, клиент получит 401 —
  обработка (разлогин и уход на экран входа) появится вместе с экранами.
