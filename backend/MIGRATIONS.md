# Миграции базы данных

Документ описывает:
1. как устроен механизм миграций;
2. как добавлять/изменять колонки БД;
3. как миграции применяются в CI;
4. риск для существующей БД.

---

## 1. Как устроен механизм миграций

Две базы данных (см. [`config_vars.docker.yaml`](configs/config_vars.docker.yaml:9)):

| База            | Сервис Docker        | Каталог миграций                               | Сид-данные                                   |
|-----------------|----------------------|------------------------------------------------|----------------------------------------------|
| `ya_brander_db_1` | `postgres`           | `postgresql/migrations/db-1/`                  | `postgresql/data/initial_data.sql`           |
| `vector_db`     | `vector-postgres`    | `postgresql/migrations/vector-db/`             | `postgresql/data/vector_initial_data.sql`    |

Механизм — [`scripts/run_migrations.sh`](scripts/run_migrations.sh:1):

- Создаёт журнал применённых миграций `schema_migrations(version, applied_at)`.
- Проходит по файлам `*.sql` в `MIGRATIONS_DIR` **в алфавитном порядке** и применяет
  только те, которых ещё нет в `schema_migrations`. Повторно уже применённые файлы
  **не выполняются** (именно поэтому сами файлы не обязаны быть идемпотентными —
  `CREATE TABLE`/`CREATE INDEX` без `IF NOT EXISTS` здесь безопасны).
- Если задан `SEED_FILE` — выполняет его **каждый раз** в конце (см. раздел «Риски»).

Локальный запуск — через `docker compose` / `make`:

```bash
make docker-start-service-debug   # поднимет БД, применит миграции и сид, запустит сервис
make migrate-all                  # применить миграции к обеим БД (без сида)
```

Сервисы [`migrate`](docker-compose.yml:22) и [`migrate-vector`](docker-compose.yml:61)
в `docker-compose.yml` — это разовые контейнеры, которые вызывают
`run_migrations.sh` и завершаются.

## 2. Как добавить / изменить колонку БД

Принцип: **никогда не правим уже применённый файл миграции.** Каждая миграция —
новый файл с увеличивающимся префиксом.

### Шаг 1. Создайте новый файл миграции

Для основной БД — в `postgresql/migrations/db-1/`, с номером на единицу больше:

```
postgresql/migrations/db-1/0002_add_user_avatar.sql
```

Для векторной БД — в `postgresql/migrations/vector-db/`:

```
postgresql/migrations/vector-db/0002_xxx.sql
```

### Шаг 2. Напишите SQL с учётом миграционных правил

- **Всегда добавляйте `IF NOT EXISTS` / `IF EXISTS`** там, где это возможно, чтобы
  файл было безопасно применять к БД, где объект уже есть (например, при ручном
  применении или откате):
  ```sql
  ALTER TABLE users ADD COLUMN IF NOT EXISTS avatar_url TEXT;
  ```
- Для изменения колонки (`ALTER COLUMN ... TYPE`) будьте аккуратны: операция может
  быть долгой и блокировать таблицу на больших данных.
- Индексы — с `IF NOT EXISTS`:
  ```sql
  CREATE INDEX IF NOT EXISTS idx_users_avatar ON users (avatar_url);
  ```
- Изменения «в лоб», которые нельзя перезапускать (без `IF NOT EXISTS`),
  допустимы только потому, что `run_migrations.sh` отслеживает применённые файлы.
  Но в целях безопасности пишите SQL так, чтобы он был максимально идемпотентным.

### Шаг 3. Проверьте локально

```bash
make docker-start-service-debug
# или только миграции без перезапуска сервиса:
make migrate-all
```

Проверьте, что в журнале появилась новая версия:

```bash
docker exec service-postgres psql -U user -d ya_brander_db_1 -c "SELECT * FROM schema_migrations ORDER BY version;"
```

### Шаг 4. Закоммитьте

Миграция попадёт в CI на push в `main` (пути `backend/**`) и применится при деплое
автоматически (см. раздел 3). **Не изменяйте** уже применённые файлы миграций и
файлы сид-данных для уже существующих данных — это сломает версионирование.

> **Совет:** если нужно изменить «полное» состояние схемы для новых окружений,
> обновите и файл-схему `postgresql/schemas/db-1.sql` / `vector-db.sql` (это
> «идеальная» схема для создания БД с нуля), но изменения существующей БД делайте
> только новым файлом миграции.

## 3. Как миграции применяются в CI

Добавлено в [`deploy-backend.yaml`](../.sourcecraft/deploy-backend.yaml) внутри
задачи `deploy` воркфлоу `build-and-deploy-backend` (см.
[`ci.yaml`](../.sourcecraft/ci.yaml:46)). Порядок шагов:

1. Доставка `postgresql/` и `scripts/` на сервер (tar-стримом по SSH) — эти файлы
   не входят в Docker-образ backend.
2. Применение миграций к **основной БД** (`ya_brander_db_1`) разовым контейнером
   `postgres:18`, который выполняет `run_migrations.sh` против `service-postgres`
   в сети `ya-brander-net`.
3. Применение миграций к **векторной БД** (`vector_db`) — только если контейнер
   `service-vector-postgres` существует (иначе пропускается, чтобы не валить деплой).
4. Деплой бэкенда (`docker pull` + `docker run ya-brander`).

Важные особенности реализации:

- **Сид-данные в проде не выполняются** — контейнеру миграций `SEED_FILE` не
  передаётся. Применяются только версионированные миграции из `migrations/`.
- Порядок гарантирован: миграции идут до запуска бэкенда, поэтому сервис
  стартует уже с актуальной схемой.
- Задача `deploy` стартует только после успешной задачи `build` (через
  `needs: [build]` в `ci.yaml`).

## 4. Риск для существующей БД

Вопрос «не сломается ли текущая база при таком запуске?» — разбор по частям.

### 4.1. Сид-данные (`TRUNCATE`) — НАСТОЯЩАЯ опасность

Файлы сидов начинаются с `TRUNCATE`:

- [`initial_data.sql`](postgresql/data/initial_data.sql:1) → `TRUNCATE TABLE users CASCADE;`
  — **удаляет всех пользователей** (каскадно: проекты, версии, подписки).
- [`vector_initial_data.sql`](postgresql/data/vector_initial_data.sql:1) → `TRUNCATE TABLE vector_examples;`.

`run_migrations.sh` выполняет сид **каждый раз**, если задан `SEED_FILE`.
Если бы CI передавал сид на прод — это **уничтожило бы все реальные данные**.
Именно поэтому в CI-шаге миграций `SEED_FILE` **намеренно не задаётся**.

> Если вы сами вручную запустите `make docker-start-service-debug` на продакшн-БД
> (или передадите `SEED_FILE`), сид затрёт данные. На проде используйте только
> `make migrate` / `make migrate-all` (без сида).

### 4.2. Уже применённая схема — защита от двойного применения

Файлы `0001_initial_schema.sql` используют `CREATE TABLE`/`CREATE INDEX` **без**
`IF NOT EXISTS`. Повторный запуск самого файла упал бы с «relation already exists».
Но `run_migrations.sh` не перезапускает уже применённые файлы: запись в
`schema_migrations` предотвращает повторное выполнение. При повторном деплое
скрипт выведет `Skip: 0001_initial_schema.sql (already applied)` и продолжит.

### 4.3. Пограничный случай: БД создана без журнала `schema_migrations`

Если схема на проде была создана вручную (например, из
[`schemas/db-1.sql`](postgresql/schemas/db-1.sql) или вручную), а журнал
`schema_migrations` не заполнен, то первый запуск попытается выполнить
`0001_initial_schema.sql` и **упадёт** на «relation already exists»
(`ON_ERROR_STOP=1`). При этом:

- `CREATE TABLE`/`CREATE INDEX` — атомарны, таблицы **не повредятся**;
- деплой упадёт (что сигнализирует: журнал нужно доинициализировать).

Лечение: разово пометить уже существующую миграцию как применённую, не выполняя её:

```bash
docker exec service-postgres psql -U user -d ya_brander_db_1 -c \
  "INSERT INTO schema_migrations (version) VALUES ('0001_initial_schema.sql') ON CONFLICT (version) DO NOTHING;"
```

После этого повторный деплой корректно пропустит `0001` и применит только новые
файлы. Аналогично для векторной БД с `0001_vector_examples.sql` в `vector_db`.

### 4.4. Векторная БД может отсутствовать

Бэкенд обращается к `service-vector-postgres` (`vector_db`). Если на сервере этой
БД нет, бэкенд не сможет использовать векторный поиск. CI-шаг для векторных
миграций не падает (пропускает), поэтому деплой пройдёт, но векторная функциональность
будет недоступна, пока не будет поднят `vector-postgres` и не применены миграции.

## Итоговая сводка

| Вопрос | Ответ |
|--------|-------|
| Применяются ли миграции в CI? | Да, после доработки — на каждом деплое (шаг 3) |
| Не сломает ли CI текущую БД? | Нет: применяются только версионированные миграции, сид (`TRUNCATE`) в проде не выполняется |
| Что делать для добавления колонки? | Новый файл `NNNN_*.sql` в `postgresql/migrations/db-1/` (или `vector-db/`), закоммитить, CI применит на деплое |
| Что делать, если схема уже есть без журнала? | Разово доинициализировать `schema_migrations` (см. 4.3) |
| Чем опасны сид-файлы? | `TRUNCATE` стирает данные — на проде их не запускать |
